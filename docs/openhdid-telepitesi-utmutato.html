1Áttekintés

Az OpenHDID egyetlen konténer-image-ként érkezik (ghcr.io/adamfhun/openhdid, linux/amd64 és linux/arm64). Ugyanaz az image minden szerepet ellát, a Compose-fájl a parancs szerint indítja a szolgáltatásokat:

SzolgáltatásParancsFeladat
webwebnginx (mainline, headers-more, TLS 1.3) és PHP-FPM egy konténerben: ügyfélportál, munkatársi panel, gépi API-k. Az nginx és a PHP-FPM Unix-socketen beszél, FastCGI-port nem nyílik.
workerworker defaultÜzenetsor-feldolgozó: e-mail, SMS, életjel.
sync-workerworker syncA panelről indított ügyféltörzs-átvétel külön soron (legfeljebb 20 perc), hogy ne tartsa fel az üzeneteket.
schedulerschedulerAz ütemező a cron helyett (php artisan schedule:work). Pontosan egy példány fusson.
migratemigrateMinden indításkor egyszer lefut: megvárja az adatbázist, lefuttatja a migrációkat és a szerepkör-seedert (amely csak bővít: a szerepkörök kézi módosításait nem állítja vissza), majd kilép. A többi szolgáltatás csak a sikeres lefutása után indul.
mariadb–Beépített MariaDB 12.3 LTS a db profillal. Külső adatbázisnál elhagyható.
valkey–Valkey (Redis-kompatibilis, BSD-licencű) a redis profillal: közös gyorsítótár, munkamenet és üzenetsor több webpéldányhoz.

A telepítési mappa tartalma: compose.yaml; .env (alkalmazás); db.env (adatbázis-rendszergazda és migrációs fiók); tls/ (saját tanúsítvány és kulcs); választhatóan ca/ (belső tanúsítványkiadók). Az image nem tartalmaz beállítást, kulcsot, tanúsítványt és dokumentációt. A dokumentáció a forrásrepó docs mappájában és minden kiadás mellékleteként érhető el.

Az image tartalma:

  • Alpine Linux 3.24, OpenSSL 3.5 (LTS);
  • PHP 8.5 FPM csak a szükséges kiterjesztésekkel: pdo_mysql, intl a teljes ICU-adattal, bcmath, zip, soap, pcntl, redis, OPcache;
  • forrásból fordított nginx mainline, csak a használt modulokkal és a beépített headers-more modullal;
  • az alkalmazás az éles függőségeivel.

Ami kimaradt: Composer, Node.js, git, fordítóeszközök, PHP-forrás, PEAR, curl-parancs, dokumentáció és tesztek. A konténer a www-data felhasználóval (uid 82) fut, csak olvasható gyökér-fájlrendszerrel; írni csak a storage kötetre és a memóriában lévő /tmp-re tud.

Docker telepítése. A disztribúció saját Docker-csomagja gyakran régi vagy hiányzik (AlmaLinux, RHEL), ezért a Docker saját tárolója ajánlott. Példa AlmaLinux 9-en (AlmaLinux 10-en a tároló felvétele dnf config-manager addrepo --from-repofile=… alakú):

sudo dnf remove -y podman podman-docker podman-compose buildah   # ha fent vannak
sudo dnf install -y dnf-plugins-core
sudo dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
sudo dnf install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo usermod -aG docker <üzemeltető felhasználó>

A docker csoport tagsága csak új bejelentkezéssel él (az id parancs mutatja), és root-joggal ér fel: ez a felhasználó csak a telepítés üzemeltetésére szolgáljon. Ellenőrzés: a docker version és a docker compose version kliens- és szerveroldalt is mutat.

Hálózat.

  • Bejövő: 443 a böngészőknek, a telefonközpontnak és a mobil kiszolgálónak; 80 csak a böngészős HTTPS-átirányításhoz kell.
  • Kimenő, a konténerekből: Exchange (EWS) vagy SMTP, Ozeki SMS-átjáró, Microsoft Entra és ADFS, az ügyféltörzs gépi felülete, valamint a DNS.
  • Az image letöltéséhez a ghcr.io kell; zárt hálózatban saját registrybe tükrözhető.
  • Proxy mögött: a Docker-démon nem örökli a felhasználó http_proxy/https_proxy változóit, a letöltés 30 másodperc után időtúllépéssel elhal; a proxyt systemd drop-innal kell megadni (üzemeltetési kézikönyv 6. fejezet). Az alkalmazás kimenő kapcsolatai (Exchange, SMS-átjáró, ADFS, Entra, ügyféltörzs) ettől függetlenül a HDID_HTTP_PROXY kulccsal mennek proxyn át, a HDID_NO_PROXY listában felsorolt belső kiszolgálók kivételével (lásd a „Külső rendszerek” táblázatot). A konténer örökölt HTTP_PROXY/HTTPS_PROXY változóit az alkalmazás nem használja.

Kliens-IP a Docker mögött. Az IP-alapú forgalomkorlát és az auditnapló a kérés valódi forráscímére épül. IPv4-en a Docker megőrzi a kliens címét. IPv6-on, kikapcsolt ip6tables vagy a userland-proxy használata mellett viszont a konténer a Docker-átjáró címét látja. Telepítés után a docker compose logs web access logjában ellenőrizze, hogy az ip mező a valódi kliens címét mutatja-e. Ha nem, kapcsolja be a Docker IPv6-NAT-ját, vagy tegye a webet egy terheléselosztó mögé (OPENHDID_TLS=off, 6.5 pont).

3Telepítés lépésről lépésre

A példák a /opt/openhdid mappát használják. A parancsokat a docker csoport tagja futtatja (2. fejezet); az alkalmazás maga nem root felhasználóként fut.

  1. A telepítési fájlok letöltése a legfrissebb kiadásból. A kiadások böngészhető oldala a https://github.com/adamfhun/openhdid/releases/latest; a lenti alapcím mindig a legfrissebb kiadás mellékleteire mutat, egy adott verzió a https://github.com/adamfhun/openhdid/releases/download/v<verzió> alapcímmel választható. Az alapcím önmagában nem megnyitható oldal (404-et ad), csak a fájlnévvel együtt él. A mappa tulajdonosa a parancsokat futtató fiók (id -un; a $USER változót nem minden shell állítja be). A .env és a db.env titkokat tartalmaz, ezért csak a tulajdonos olvashatja: 
    sudo mkdir -p /opt/openhdid && sudo chown "$(id -un)" /opt/openhdid && cd /opt/openhdid
base=https://github.com/adamfhun/openhdid/releases/latest/download
curl -fsSL -O "$base/compose.yaml"
curl -fsSL -o .env "$base/env.example"
curl -fsSL -o db.env "$base/db.env.example"
curl -fsSL -O "$base/backup.sh"
chmod 600 .env db.env
chmod 755 backup.sh
    A backup.sh a mentés és a visszaállítás szkriptje (üzemeltetési kézikönyv 7. fejezet).
  2. Kötelező értékek a .env fájlban:
    • OPENHDID_VERSION: a letöltött env.example-ben már a kiadás pontos verziószáma áll (a releases/latest mindig a legfrissebb kiadás fájljait adja), ezt nem kell kikeresni; latest-re ne írja át;
    • APP_URL: a webhely HTTPS-címe, ebből képződik a kiszolgálónév is;
    • DB_PASSWORD: a futási adatbázis-fiók jelszava;
    • a levelezés, az SMS és az ügyféltörzs beállításai (5. fejezet).
    A db.env fájlban a MARIADB_ROOT_PASSWORD és a migrációs fiók jelszava (DB_PASSWORD) kell. Mindhárom jelszó egyedi, hosszú és véletlenszerű legyen, például openssl rand -base64 32. Mindhárom titok fájlból is megadható (MARIADB_ROOT_PASSWORD_FILE, DB_PASSWORD_FILE a db.env-ben és a .env-ben), lásd a 4. fejezet „Titkok fájlból” pontját.
  3. Mappák és az image letöltése. A tanúsítvány (tls) és a belső tanúsítványkiadók (ca) mappáját a telepítő fiók hozza létre: a Compose a hiányzó csatolt mappát root tulajdonnal hozná létre, és a tanúsítvány másolása a következő lépésben elbukna. Az image a ghcr.io-ról jön (zárt hálózatban a 2. fejezet szerint tükrözött registryből); az alkalmazáskulcsot is ez az image készíti, ezért a letöltés már itt kell: 
    mkdir -p tls ca
docker compose pull
  4. Alkalmazáskulcs. Egyszer kell létrehozni. A kimenetet írja a .env APP_KEY sorába, és őrizze meg a mentésektől elkülönített, védett helyen: 
    docker compose run --rm --no-deps web key
    Image nélkül ugyanilyen kulcsot ad: echo "base64:$(openssl rand -base64 32)". A kulccsal titkosított adatok (biztonsági válaszok, kódmásolatok, API-tokenek) nélküle nem olvashatók vissza. Meglévő telepítésen soha ne cserélje.
  5. Tanúsítvány. A teljes lánc és a kulcs a tls mappába kerül. A konténer felhasználójának (uid 82) olvashatónak kell lennie: 
    cp /utvonal/fullchain.pem /utvonal/privkey.pem tls/
sudo chown 82:82 tls/fullchain.pem tls/privkey.pem
sudo chmod 444 tls/fullchain.pem && sudo chmod 400 tls/privkey.pem
    Sudo nélkül vagy rootless Dockerrel a fájlokat az alkalmazás saját felhasználója írja a mappába, így a tulajdonos az lesz, akit a konténer lát (rootless Dockernél a 82-es felhasználó a gazdagépen egy névtér-azonosító, ezért ott a sudo chown 82:82 nem jó). A mappa csak erre az időre nyílik meg: 
    chmod 777 tls
docker compose run --rm --no-deps -T -v "$PWD/tls":/t --entrypoint sh web -c 'cat > /t/fullchain.pem && chmod 444 /t/fullchain.pem' < /utvonal/fullchain.pem
docker compose run --rm --no-deps -T -v "$PWD/tls":/t --entrypoint sh web -c 'cat > /t/privkey.pem && chmod 400 /t/privkey.pem' < /utvonal/privkey.pem
chmod 755 tls
  6. Belső tanúsítványkiadók (választható). Ha az Exchange, az ADFS, az ügyféltörzs vagy a külső adatbázis belső CA-val hitelesít, a CA-tanúsítványt tegye a ca mappába (*.crt vagy *.pem). Indításkor a rendszer tanúsítványtára mellé kerül; a TLS-ellenőrzés kikapcsolására nincs szükség.
  7. Indítás (az image a 3. lépésben már letöltődött): 
    docker compose up -d
docker compose ps
    Az első indításkor sorrendben:
    1. a MariaDB létrehozza az adatbázist és a két fiókot;
    2. a migrate lefut, majd kilép (exited (0));
    3. a web, worker, sync-worker és scheduler elindul; a web állapota egy percen belül healthy.
  8. Az első rendszergazda (jelszót kér, legalább 12 karakter): 
    docker compose exec web php artisan hdid:make-admin admin@example.org --name="Rendszergazda"
    A parancs helyi ügyféltörzsbeli tételt is létrehozza, így a belépési szabály teljesül; a későbbi ügyféltörzs-átvételek ezt a helyi tételt nem tekintik hiányzónak, és ha az e-mail-cím az ügyféltörzsben is megjelenik, a fiókot átkötik rá. A jelszót rejtett prompt kéri; ha a belépés „hibás felhasználónév vagy jelszó” hibát ad, a parancs ugyanarra az e-mailre újrafuttatva új jelszót állít, a valódi elutasítási ok pedig az auditnaplóból kérdezhető le (üzemeltetési kézikönyv 6. fejezet). Ha a web még nem fut, a parancs docker compose run --rm --no-deps web artisan hdid:make-admin … alakban is megy.
  9. Első ellenőrzés és a telefonközpont kulcsa (a kulcs egyszer jelenik meg): 
    docker compose exec web php artisan hdid:health
docker compose exec web php artisan hdid:api-key:create "Prémium telefonközpont" callcenter
  10. Belépés a https://<kiszolgáló>/admin címen, majd az első beállítás a 10. fejezet szerint, végül az átvételi ellenőrzés a 12. fejezet szerint.

4A beállítások működése a kész csomagban

A beállítások két rétegben élnek.

  • Telepítési értékek: címek, jelszavak, illesztők, ütemezés, hálózat. Környezeti változók a .env fájlban.
  • Üzleti paraméterek: csomaglisták, azonosítási határok, arculat, adatmegőrzés, belépési módok. A felületen, az Adminisztráció › Rendszer › Beállítások alatt szerkeszthetők, az adatbázisban tárolódnak.

Ez a szétválasztás a konténerben is ugyanaz, mint a hagyományos telepítésnél.

  1. Átadás. A Compose a .env minden sorát környezeti változóként adja át a konténereknek (env_file). Ugyanebből a fájlból olvassa a saját változóit is (OPENHDID_VERSION, portok, profilok). A db.env-t csak a mariadb és a migrate szolgáltatás kapja meg. A konténeren belül nincs .env fájl, a Laravel a folyamat környezetét olvassa.
  2. Biztonságos alapértékek. Az image-ben beállított alapértékek: APP_ENV=production, APP_DEBUG=false, LOG_CHANNEL=stderr. Amit a .env nem ad meg, az ezekkel indul.
  3. Titkok fájlból. Bármely változó megadható fájlként is: NÉV_FILE=/run/secrets/…. Indításkor a NÉV változó a fájl tartalmát kapja; ha a kettőt egyszerre adja meg, az hiba. Docker- és Kubernetes-titkokhoz ajánlott, mert a sima környezeti változót a docker inspect megmutatja. Ugyanez érvényes a beépített MariaDB fiókjaira: a db.env-ben a MARIADB_ROOT_PASSWORD_FILE és a migrációs fiók DB_PASSWORD_FILE (vagy DB_USERNAME_FILE) kulcsa, a .env-ben a futási fiók DB_PASSWORD_FILE kulcsa használható; az első induláskor a fiókkészítő szkript a fájlok tartalmával hozza létre a fiókokat. A titokfájlt ekkor a mariadb és a migrate konténerbe is csatolni kell ugyanazon az útvonalon (Compose secrets vagy kötet), nem csak az alkalmazás-konténerekbe.
  4. Ellenőrzés induláskor. Minden szerepkör indulásakor az indítószkript megnézi a kötelező értékeket, és hibás beállítással a konténer érthető hibaüzenettel leáll (docker compose logs). Hibának számít:
    • az érvénytelen APP_KEY;
    • ha az APP_URL nem https;
    • a hiányzó adatbázis-adat;
    • az ismeretlen APP_ENV érték: csak production, staging, demo, local vagy testing lehet, mert például a prod vagy a Production az éles védelmeket csendben kikapcsolná;
    • élesben (APP_ENV=production) az APP_DEBUG=true, a mindenkit megbízhatónak vevő TRUSTED_PROXIES (*, **, 0.0.0.0/0, ::/0), a SESSION_SECURE_COOKIE=false, az üres DB_PASSWORD (socketes kapcsolat kivételével), és ha a gyorsítótár, a sor vagy a munkamenet Redis-t használ, az üres REDIS_PASSWORD. A konténer ilyenkor 64-es kilépési kóddal áll meg, és a restart szabály miatt újraindulgat; az ok a docker compose logs web kimenetében. Részletes hibaüzenetekhez az üzemeltetési kézikönyv 5. fejezetének hibakeresési receptje való, nem a production környezet debug módja.
    Csak figyelmeztetés jár a naplóba író levélküldésért és SMS-ért, valamint az önaláírt tanúsítványért.
  5. Gyorsítótár. Az ellenőrzés után a konfiguráció, az útvonalak és az események gyorsítótára a memóriában lévő /tmp-be épül. A titkokat is tartalmazó konfigurációs gyorsítótár így lemezre sem kerül. A PHP-FPM dolgozói ezt olvassák, a konténer környezetét nem látják (clear_env).
  6. Módosítás: a .env szerkesztése után docker compose up -d. A Compose az érintett konténereket újraindítja, a gyorsítótár újraépül; a hagyományos php artisan optimize és queue:restart itt nem kell. A felületi beállítások azonnal élnek, újraindítás nélkül.

APP_KEY Soha nem generálódik magától, és meglévő telepítésen nem cserélhető: cseréje a titkosított adatok, a kulcsolt keresőlenyomatok és az ügyféltörzs tokenjeinek elvesztésével jár. A mentés része legyen, a mentéstől elkülönített hozzáféréssel.

5Környezeti változók

A teljes lista magyar magyarázattal a kiadás env.example fájljában található. A legfontosabbak:

Backslash az értékben. Tartományi felhasználónevet (DOMAIN\user, például az ügyféltörzs vagy az NTLM-es Exchange fiókja) idézőjel nélkül vagy aposztrófok között írjon: EMD_SYNC_USERNAME=DOMAIN\user vagy EMD_SYNC_USERNAME='DOMAIN\user'. Dupla idézőjelben a Compose a \n és \r sorozatot sortöréssé alakítja, így a "DOMAIN\nagy" két sorra esik. Az alkalmazás a nevet JSON-ban, helyesen kódolva küldi, a backslash-t nem kell kettőzni.

6Hálózat, kiszolgálónév és HTTPS

6.1 Figyelő cím és portok

A konténerben az nginx mindig ugyanazokon a nem privilegizált portokon figyel: 8080 (HTTP) és 8443 (HTTPS), minden konténercímen. Ezekhez nem kell hozzányúlni.

Hogy a gazdagép melyik címén és portján érhető el a szolgáltatás, azt a Compose port-leképezése dönti el a .env alapján:

OPENHDID_BIND_IP=192.0.2.10    # egyetlen hálózati kártya címe; 0.0.0.0 = minden IPv4-cím
OPENHDID_HTTPS_PORT=443
OPENHDID_HTTP_PORT=80

Ha a 80-as portra egyáltalán nincs szükség, a compose.yaml web szolgáltatásából törölheti a 8080-as leképezést, vagy az OPENHDID_HTTP_REDIRECT=false minden HTTP-kérést elutasít. A 443-as porton a tűzfal engedje a klienseket, a telefonközpontot és a mobil kiszolgálót; az adatbázis és a Valkey portja nincs kivezetve a gazdagépre.

6.2 Kiszolgálónév (domain)

  • A kiszolgálónév az APP_URL hostjából képződik; ez az egyetlen hely, ahol meg kell adni. További nevek az OPENHDID_EXTRA_HOSTS változóban adhatók meg (a tanúsítványnak ezeket is le kell fednie).
  • Ismeretlen Host fejléc vagy SNI: a TLS-kézfogás elutasítva, HTTP-n kapcsolatbontás (444). Idegen név alatt az alkalmazás nem szolgálható ki.
  • A 80-as porton csak a böngészős GET/HEAD kérés kap 308-as átirányítást az APP_URL címére. A gépi (/api/) és hitelesítési (/auth/) útvonalak, illetve minden más metódus kapcsolatbontást kap.
  • Az nginx-konfigurációt az indítószkript minden induláskor a környezetből állítja elő, csak ellenőrzött értékekkel, majd nginx -t próbát futtat. Kézi szerkesztésre nincs szükség.

6.3 HTTPS saját tanúsítvánnyal (TLS 1.3)

Alapértelmezés (OPENHDID_TLS=on): a tls/fullchain.pem (a kiszolgáló tanúsítványa, utána a köztes tanúsítványok) és a tls/privkey.pem. Induláskor a rendszer ellenőrzi:

  • a kulcs a tanúsítványhoz tartozik-e;
  • a tanúsítvány lefedi-e az APP_URL és az extra neveket (a SAN-ban, helyettesítő névvel is);
  • a tanúsítvány érvényes-e már, és nem járt-e le; 30 napon belüli lejáratnál figyelmeztet;
  • a kulcs típusát és méretét (RSA legalább 2048 bit);
  • van-e köztes tanúsítvány a fájlban.

Hibánál a web nem indul, és a napló megmondja az okot. Kézi próba a futó rendszeren:

docker compose exec web openhdid tls-check

A parancs az OPENHDID_TLS=on módhoz tartozik: selfsigned és off módban nincs mit ellenőriznie, a hiányzó tanúsítványfájl miatt hibával lép ki.

A beállítás kizárólag TLS 1.3-at fogad (TLS_AES_256_GCM_SHA384, TLS_CHACHA20_POLY1305_SHA256, TLS_AES_128_GCM_SHA256). Early data és session ticket nincs. A kulcscsere elsődlegesen az X25519MLKEM768 poszt-kvantum hibrid eljárás, ezt a friss böngészők és az OpenSSL 3.5 támogatja, a régebbi kliensek az X25519-re esnek vissza. Minden HTTPS-válasz HSTS-fejlécet kap (1 év, aldomainekkel). A TLS 1.2 engedélyezése csak dokumentált döntéssel és klienspróbával jöhet szóba, régi partner miatt sem kerülhet vissza a TLS 1.0/1.1.

Tanúsítványcsere: a fájlok cseréje után kapcsolatbontás nélküli újratöltés, amely előtte ellenőriz:

docker compose exec web openhdid reload

Automatikus megújításnál (például ACME DNS-01 a gazdagépen) ezt a parancsot kösse a megújítás utáni lépéshez. A konténer nem nyit ACME HTTP-01 útvonalat.

6.4 Fejlécek és a kiszolgáló azonosítóinak elrejtése

Az nginx forrásból, csak a szükséges modulokkal készül; a headers-more modul be van fordítva.

  • Server és X-Powered-By: egyik válaszban sincs, a hibaválaszokban sem (server_tokens off, more_clear_headers, expose_php=Off, fastcgi_hide_header).
  • Biztonsági fejlécek minden válaszon egyszer: HSTS, nosniff, X-Frame-Options DENY, Referrer-Policy, Permissions-Policy, Cross-Origin-Opener-Policy, CSP és X-Robots-Tag.
  • Gyorsítótár: a dinamikus válaszokon Cache-Control: no-store; a tartalomhash-elt statikus fájlok egy évig gyorsítótárazhatók, előtömörítve.
  • Hibák és tiltások: saját, termék- és verziómentes hibaoldal; csak az index.php futtatható, a pontos nevű fájlok nem érhetők el, a TRACE 405.
  • Access log: nem tárol URL-t, lekérdezést, Referert, sütit és kéréstörzset.

6.5 Terheléselosztó vagy fordított proxy mögött

OPENHDID_TLS=off esetén a konténer csak a 8080-as porton, HTTP-n szolgál ki. A TLS-t ekkor a terheléselosztó zárja le, és ott is TLS 1.3 legyen.

  • TRUSTED_PROXIES: a terheléselosztó címei vagy CIDR-tartománya; a * nem használható. Az nginx csak ezektől fogadja el az X-Forwarded-For kliens-IP-t; a PHP felé minden kérés HTTPS-ként megy, mert a nyilvános cím HTTPS.
  • A 8080-as port csak a terheléselosztó felől legyen elérhető (tűzfal vagy belső hálózat).
  • Kulcsok: a tanúsítvány és a kulcs a terheléselosztón él. Ha a belső szakaszt is titkosítani kell, maradjon OPENHDID_TLS=on a konténerben is (újratitkosítás vagy TLS-átengedés).

6.6 Felügyeleti végpontok

A /health (az összes ellenőrzés állapota, 200 vagy 503) és a /up csak a konténeren belülről (127.0.0.1) és az OPENHDID_MONITORING_ALLOW címeiről érhető el, mások 404-et kapnak. A gazdagépről a közzétett porton érkező kérés a Docker-híd átjárócíméről jön (a docker network inspect openhdid_default mutatja, például 172.18.0.1), ezért ezt a címet kell a listába venni, különben a gazdagépről is 404 a válasz; a docker compose exec web php artisan hdid:health a listától függetlenül működik. A konténer saját egészség-ellenőrzése egy csak a konténeren belül elérhető porton fut, és nem függ ettől a listától.

6.7 Belső nevek feloldása a konténerből

A konténer a Docker beépített DNS-én át a gazdagép DNS-kiszolgálóit kérdezi, ezért a belső DNS-ben szereplő nevet (Exchange, ADFS, ügyféltörzs, SMS-átjáró, külső adatbázis) magától feloldja; nem kell minden nevet felvenni. A gazdagép /etc/hosts bejegyzéseit viszont nem látja.

  • A név csak a gazdagép /etc/hosts-ában van (teszt gépen gyakori): extra_hosts egy, a compose.yaml mellé tett compose.override.yaml-ban a web, worker, sync-worker és scheduler szolgáltatásnak, majd docker compose up -d. A Compose a felülíró fájlt magától összefésüli, a kiadott compose.yaml érintetlen marad. Tartósan jobb, ha a név a belső DNS-be kerül.
  • A gazdagép helyi feloldót használ (a /etc/resolv.conf-ban csak 127.0.0.x áll, például systemd-resolved), vagy a belső DNS csak VPN-en át érhető el: a Dockernek a /etc/docker/daemon.json dns kulcsában egyszer kell megadni a belső DNS-kiszolgálókat (meglévő fájlnál abba felvéve), majd sudo systemctl restart docker és docker compose up -d --force-recreate. Így egyetlen nevet sem kell egyenként felvenni.

Egy név vizsgálata (gazdagép kontra konténer), a compose.override.yaml-minta és a daemon.json-parancsok a kiadás TROUBLESHOOTING.md mellékletében.

7Adatbázis (MariaDB)

7.1 Beépített adatbázis

Indítás és kötet. A COMPOSE_PROFILES=db a mariadb:12.3 LTS image-et indítja digesttel rögzítve, a db nevű kötettel. A port a gazdagépre nincs kivezetve.

Első induláskor a MariaDB létrehozza:

  • a DB_DATABASE adatbázist utf8mb4_unicode_ci rendezéssel;
  • a migrációs fiókot (a db.env DB_USERNAME/DB_PASSWORD értéke), minden joggal az adatbázison;
  • a futási fiókot (a .env DB_USERNAME/DB_PASSWORD értéke), csak SELECT, INSERT, UPDATE, DELETE joggal.

Ki melyik fiókot használja. A web, a worker és a scheduler csak a futási fiókot látja, sémát nem módosíthat. A migrációk a migrációs fiókkal futnak.

Kiszolgálóbeállítás. Karakterkészlet, skip-name-resolve, puffer (OPENHDID_DB_BUFFER_POOL, a gép memóriájának 25–50%-a) és kapcsolatszám (OPENHDID_DB_MAX_CONNECTIONS).

Csak az első induláskor. A fiókokat és az adatbázist a MariaDB az üres kötet első indításakor hozza létre. Jelszócseréhez később a mariadb konténerben ALTER USER kell, és a .env/db.env ezzel egyezzen. Fájlból adott titoknál (*_FILE) a fájl tartalma számít, ezért jelszócserénél a fájlt és az adatbázis-fiókot együtt kell módosítani.

7.2 Külső adatbázis

A COMPOSE_PROFILES üres (vagy csak redis). A DB_HOST a kiszolgáló neve. Az adatbázist és a két fiókot előre kell létrehozni:

CREATE DATABASE openhdid CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'openhdid'@'10.0.0.%' IDENTIFIED BY '…futási jelszó…';
GRANT SELECT, INSERT, UPDATE, DELETE ON openhdid.* TO 'openhdid'@'10.0.0.%';
CREATE USER 'openhdid_migrate'@'10.0.0.%' IDENTIFIED BY '…migrációs jelszó…';
GRANT ALL PRIVILEGES ON openhdid.* TO 'openhdid_migrate'@'10.0.0.%';

A hálózaton át a kapcsolat legyen TLS-es: kényszerítse a kiszolgálón (REQUIRE SSL vagy require_secure_transport), a CA-fájlt tegye a ca mappába, és adja meg a MYSQL_ATTR_SSL_CA=/etc/openhdid/ca/<fájl> értéket. A db.env ekkor is kell a migrációs fiókhoz; a MARIADB_ROOT_PASSWORD üresen maradhat.

7.3 Migrációk

  • Mikor fut: a migrate szolgáltatás minden docker compose up alkalmával lefut. Ha nincs új migráció, nem változtat semmin.
  • Mit csinál: legfeljebb 120 másodpercig vár az adatbázisra (OPENHDID_DB_WAIT_SECONDS), futtatja a migrációkat, felveszi a hiányzó jogosultságokat és beépített szerepköröket (a kézi módosításokat megőrzi), és a db.env migrációs fiókjával dolgozik.
  • Sikertelen migráció: ha a migrate nem 0-val lép ki, a web és a háttérfolyamatok nem indulnak (docker compose logs migrate).
  • Csak előre: a migrációk csak előre futnak; visszalépéshez a frissítés előtti mentés kell.
  • Egyszerre egy: egyszerre csak egy migrate fusson; Kubernetesben egyetlen Job, nem a webpodok indulása.

8Háttérfolyamatok és ütemezés (a cron helyett)

A konténerekben nincs cron-démon, és a gazdagépen sem kell crontab-bejegyzés. Az ütemezett feladatokat a scheduler szolgáltatás futtatja (php artisan schedule:work): percenként végrehajtja az alkalmazás ütemezését.

Aktiválás: a feladatok maguktól élnek, amíg a scheduler fut; ez az alap Compose-telepítés része. Környezeti változóból csak két feladat állítható, a többi időzítése rögzített:

  • EMD_SYNC_CRON: a teljes átvétel cron-kifejezése; üresen csak kézi átvétel van;
  • EMD_SYNC_TOKEN_KEEP_ALIVE: a tokenfrissítés be- és kikapcsolása.

Az időpontok az APP_TIMEZONE szerint értendők.

Ellenőrzés: docker compose exec scheduler php artisan schedule:list, valamint a Rendszerállapot oldal „Ütemező” és „Feladatsor” kártyája, amely a percenkénti életjelből dolgozik.

Az ütemezőből mindig pontosan egy példány fusson. A kritikus feladatok a közös gyorsítótár záraival védettek (withoutOverlapping, onOneServer), így egy véletlen második példány sem futtatja őket kétszer, de ettől még nem kívánatos.

A worker és a sync-worker:

  • óránként szabályosan kilépnek (--max-time=3600), és a Compose újraindítja őket; így a memória nem nő korlátlanul;
  • minden feladat előtt újraolvassák a felületi beállításokat;
  • a panelről indított ügyféltörzs-átvétel csak akkor fut, ha a sync-worker fut, és az EMD_SYNC_QUEUE értéke sync; különben a rendszerállapot 5 perc várakozás után figyelmeztet.

9Naplók

Minden folyamat a konténer szabványos kimenetére ír, fájlba nem. A konténermotor gyűjti és forgatja a naplókat: a compose.yaml json-file naplózó-meghajtót használ, szolgáltatásonként legfeljebb 10 × 20 MB-tal (Podman alatt ez a k8s-file, ott csak a méretkorlát él). Beállítás nélkül a naplók korlátlanul nőnének; a Docker saját local meghajtóját a Podman nem ismeri.

ForrásFormátumOlvasás
nginx access logsoronként JSON: idő, kliens-IP, kérésazonosító, metódus, státusz, méret, időtartamdocker compose logs -f web
nginx hibák, PHP-FPM, alkalmazásszöveges sorok; az alkalmazás JSON-ra is állítható (LOG_STDERR_FORMATTER=Monolog\Formatter\JsonFormatter)docker compose logs web
üzenetsor-feldolgozókszöveges sorokdocker compose logs -f worker sync-worker
ütemezőszöveges sorokdocker compose logs scheduler
migráció, adatbázisszöveges sorokdocker compose logs migrate mariadb

Hasznos szűrések:

docker compose logs --since 1h web                   # az utolsó óra
docker compose logs --no-log-prefix web | grep '"status":5'   # szerverhibák
docker compose logs --no-log-prefix web | grep -v '^{' # minden, ami nem access log (hibák, figyelmeztetések)
docker compose logs -f --tail=100 worker            # élő követés

Központi naplógyűjtés. Az ASVS V16 elkülönített, módosítás ellen védett tárolást vár. A compose.yaml x-logging blokkjában a meghajtó cserélhető, például journald, syslog (TLS-sel), gelf vagy fluentd; a Docker-démon szintjén is beállítható. Az access log nem tartalmaz URL-t és titkot. Az nginx hibasorai és az alkalmazás hibaszövegei viszont tartalmazhatnak URL-t vagy személyes adatot, ezért a továbbításuk korlátozott hozzáféréssel történjen.

Fájlnapló (ha a szervezet ezt kéri): LOG_STACK=stderr,daily és LOG_CHANNEL=stack. A napi fájlok ekkor a storage köteten keletkeznek (storage/logs), 30 napos megőrzéssel.

10Első beállítás a felületen

Belépés a /admin címen az első rendszergazdával, majd az Adminisztráció › Rendszer › Beállítások alatt, ebben a sorrendben:

  1. Csomagok: a prémium (és ha van, a normál) csomagnevek listája. Csomaglista nélkül egyetlen ügyfél sem tud belépni.
  2. Ügyfélszolgálat: szintenként e-mail-cím, telefonszám, nyitvatartás.
  3. Arculat és Prémium: alkalmazásnév, embléma, böngészőikon, színek, háttérképek. Az alapértelmezés semleges színséma; a levelek és a kimutatások is a beállított színeket használják.
  4. Portál: jogi név, lábléc, adatkezelési és felhasználási hivatkozások.
  5. Ügyfél belépés és SSO: mely belépési módok élnek. Az SSO bekapcsolása előtt a környezeti változók legyenek kitöltve.
  6. Ügyféltörzs (EMD): munkatársi és ügyfél-domainlista, oszlopmegfeleltetés, védőkorlátok, CSV-kódolás, az export és az ID-lista kéréstörzse, az ID-lista válaszútvonalai és kijelölése (az ügyféltörzs-átvétel kezelésére jogosult munkatárs).
  7. Azonosítás, Hívások, Adatmegőrzés: az alapértékek a próbaüzemre megfelelnek. Az ügyintézői sikertelen ellenőrzések korlátja alapból 50 óránként.

Ezután: Tartalom › Üzenetsablonok (próbaküldés), Rendszer › API-kulcsok, Fiókok (munkatársak, szerepkörök), Azonosítás › Kérdések. A felület részletes leírása a felhasználói kézikönyvben található.

11Külső rendszerek bekötése

A konténerben futó parancsok előtagja docker compose exec web php artisan.

Ügyféltörzs (Enterprise Master Data, EMD)

  1. Töltse ki az EMD_SYNC_* értékeket (jelentésük az 5. fejezet táblázatában), majd docker compose up -d. Az export és az ID-lista kéréstörzse nem környezeti változó: a panel Beállítások › Ügyféltörzs (EMD) fülén áll.
  2. A belépés ellenőrzése: docker compose exec web php artisan hdid:emd-sync-token.
  3. Próbafuttatás: docker compose exec web php artisan hdid:emd-sync --dry-run, vagy a panel Próbafuttatás az API-ból gombja; utóbbi a sync-worker-en fut.
  4. Megfelelő eredmény után az éles átvétel.

A védőkorlátok, a domainszűrés és a hibakezelés az üzemeltetési kézikönyv 6. fejezetében olvashatók.

Levelezés

MAIL_MAILER=ews az EWS_* értékekkel, vagy smtp a MAIL_HOST, MAIL_PORT, MAIL_USERNAME, MAIL_PASSWORD és MAIL_SCHEME értékekkel. A feladó a MAIL_FROM_ADDRESS. Próba az ügyfelek érintése nélkül:

docker compose exec web php artisan hdid:test-mail sajat@example.org --now

SMS (Ozeki NG)

SMS_DRIVER=ozeki, az átjáró HTTPS-címe, felhasználó és jelszó. Próba: docker compose exec web php artisan hdid:test-sms +36301234567 --now. Az átjáró felé POST-kérés megy, a hozzáférés nem kerül a címsorba.

Egyszeri bejelentkezés (Entra ID, ADFS)

Négy alkalmazás-regisztráció kell: Entra és ADFS, munkatársaknak és ügyfeleknek külön. A mobilalkalmazás saját nyilvános ügyfélazonosítót kap.

Visszatérési cím: https://<kiszolgáló>/auth/{user|client}/{entra|adfs}/callback.

Entra-bérlő:

  • a saját címtár GUID-ja kell (domain, common vagy organizations nem jó);
  • a regisztráció legyen egybérlős;
  • az email igény csak ellenőrzött állapotban számít, különben a felhasználónév (UPN) dönt.

Telefonközpont és automata menü

Kulcs. A panelen Rendszer › API-kulcsok, „Call center / IVR” hatókörrel; vagy parancssorból: docker compose exec web php artisan hdid:api-key:create "Telefonközpont" callcenter. A kulcs egyszer jelenik meg.

Küldés. A kulcs az X-Api-Key fejlécben küldendő. Az api_key lekérdezési paraméter csak örökölt partnernek használható, mert webszerver-naplóba kerülhet; az access log itt nem rögzíti.

Aláírás. Választható HMAC-aláírás: X-Timestamp és X-Signature fejléc. Az aláírandó szöveg: időbélyeg, metódus, kéréscím a lekérdezéssel, törzs.

Leírás. A teljes gépi felület rendszergazdával belépve a /docs/ivr címen olvasható, a mobil kiszolgálóé a /docs/mobile címen. A megjelenítőt a böngésző az unpkg.com címről tölti be (a tartalombiztonsági szabályzat ezt csak a /docs/* oldalakon engedi), ezért a munkaállomásnak internet-elérés kell; zárt hálózaton a /docs/ivr.json letölthető, és bármely OpenAPI-nézőben olvasható, ez adható át a telefonközpont szállítójának is.

12Ellenőrzés és biztonsági átvétel

12.1 Működés

  • docker compose ps: a web healthy, a worker, sync-worker, scheduler és mariadb fut, a migrate exited (0).
  • docker compose exec web php artisan hdid:health kilépési kódja 0; a Rendszerállapot oldalon az adatbázis, gyorsítótár, üzenetsor és ütemező zöld (az ütemező az első percben még piros lehet). Ha az ügyféltörzs API-belépése nincs beállítva (csak fájlimport), a „Belépés az ügyféltörzs API-jába” csempe piros marad, és a kód 2.
  • A Rendszerállapot fejlécében a futó verzió látszik (a telepített kiadás száma, „Verzió: …”).
  • Próbalevél és próba-SMS megérkezik; a Kimenő üzenetek listában „elküldve”.
  • Az ügyféltörzs próbafuttatása hihető számokat ad, az éles átvétel sikeres.
  • Egy ügyfélnek küldött belépési hivatkozás beléptet a portálra; bekapcsolt SSO-nál a belépés végigmegy.
  • Telefonközponti próbahívás megjelenik a vezérlőpulton.
  • A docker compose logs web access logjában a kliensek valódi IP-címe látszik (2. fejezet).

12.2 Biztonsági próbák a gazdagépről

H=hdid.example.org
curl -sS -D - -o /dev/null https://$H/login          # 200, Cache-Control: no-store
curl -sS -D - -o /dev/null https://$H/favicon.ico    # 200
curl -sS -D - -o /dev/null https://$H/nincs.css      # 404, saját hibaoldal
curl -sS -o /dev/null -w '%{http_code}\n' -X TRACE https://$H/   # 405
curl -sS -o /dev/null -w '%{http_code}\n' https://$H/.env        # 404
curl -sS -D - -o /dev/null http://$H/login           # 308 https://$H/login
openssl s_client -connect $H:443 -servername $H -tls1_3 -verify_return_error -brief </dev/null   # siker
openssl s_client -connect $H:443 -servername $H -tls1_2 -brief </dev/null                        # elutasítva

Elvárás: egyetlen válaszban sincs Server vagy X-Powered-By fejléc; a HSTS és a többi biztonsági fejléc pontosan egyszer szerepel; ismeretlen kiszolgálónévre a kézfogás elutasított. Belső CA esetén a CA-fájlt adja át (--cacert, -CAfile); a -k nem elfogadható bizonyíték.

13Kipróbálás demóadatokkal

Tanúsítvány és külső rendszerek nélküli kipróbáláshoz a .env értékei:

OPENHDID_TLS=selfsigned

Az indítás után a migráció egyszer betölti a demóadatokat:

  • ügyintéző: agent@example.test, jelszó password-agent-1;
  • prémium ügyfél: anna@example.test, PIN 123456;
  • normál ügyfél: bela@example.test;
  • két hét hívástörténet.

Rendszergazdát a 3. fejezet 8. lépése szerint hozzon létre. A böngésző figyelmeztet az önaláírt tanúsítványra. A kimenő e-mailek és SMS-ek a docker compose logs worker kimenetében olvashatók. 14Frissítés új verzióra

Minden kiadás mellékleteként jön egy UPGRADE.md: ugyanezek a lépések másolható parancsokkal, az adott kiadás verziószámával kitöltve (letöltés ellenőrzőösszeggel, az új telepítési kulcsok listája, visszalépés).

  1. Olvassa el a kiadási jegyzetet (GitHub Releases, CHANGELOG.md). Választhatóan ellenőrizze az image aláírását (üzemeltetési kézikönyv 8. fejezet).
  2. Mentés: ./backup.sh (adatbázis, storage kötet, beállítások, tls; üzemeltetési kézikönyv 7. fejezet). Ha a frissítés után vissza kell lépni: ./backup.sh restore.
  3. Az OPENHDID_VERSION átírása az új verzióra, majd: 
    docker compose pull
docker compose up -d
docker compose ps
    A migrate lefuttatja az új migrációkat, utána a szolgáltatások az új image-dzsel indulnak újra. Egyetlen webpéldánynál ez néhány másodperces kiesés; kiesés nélküli frissítéshez több példány kell terheléselosztó mögött.
  4. Ellenőrzés a 12.1 pont szerint.

A platform frissítése (PHP, nginx, OpenSSL, Alpine) új javítóverzióként jelenik meg, a frissítés menete ugyanez. A kiadott címkék soha nem változnak, ezért egy telepítés mindig pontosan reprodukálható.
